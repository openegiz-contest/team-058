# OreFlow KZ 2.0 — How to upgrade an existing running Team 058 mine

**This is a full-project upgrade**, based on `OreFlow_Team058_Download_Fresh_20261024.zip`, not the smaller cleaned fork. The untouched base OpenEgiz infrastructure and the 102 digital-twin definitions are preserved. Existing database volumes and credentials must remain unchanged.

## Upgrade your *running* `oreflow58` installation in Ubuntu WSL

1. Download this v2 ZIP and extract it alongside (NOT over) the previous project.

```bash
mkdir -p ~/OreFlow_Team058_V2
unzip -o /mnt/c/Users/dzzen/Downloads/OreFlow_KZ_Team058_V2_24h.zip -d ~/OreFlow_Team058_V2
```

2. Copy the old `.env` **locally**. It contains the existing Ditto, InfluxDB and Grafana credentials; DO NOT paste its contents into a chat or include it in a ZIP.

```bash
cp ~/OreFlow_Team058/team-058-main/deploy/compose/.env \
   ~/OreFlow_Team058_V2/team-058-main/deploy/compose/.env
```

3. Replace just the OreFlow simulator and Grafana application containers **without deleting Docker volumes**:

```bash
cd ~/OreFlow_Team058_V2/team-058-main
COMPOSE_PROJECT_NAME=oreflow58 bash scripts/oreflow-upgrade-running.sh
```

4. Open the [mine dashboard](http://localhost:8099) and [Grafana](http://localhost:3000/d/oreflow-northpit). In a new terminal:

```bash
cd ~/OreFlow_Team058_V2/team-058-main
python3 tools/verify-oreflow.py
```

The upgrade does not reset MongoDB, Ditto, InfluxDB or Grafana data. **Do not run `docker compose down -v`, `make clean` or `docker system prune --volumes`.** Keep the old project folder as a rollback reference. If an optional Telegraf instance is missing, run `docker compose -p oreflow58 --env-file deploy/compose/.env -f deploy/compose/docker-compose.yml -f team/oreflow/compose.yml up -d telegraf` after verifying Ditto connectivity.

## First-time installation on a computer without the old stack

```bash
cd ~/OreFlow_Team058_V2/team-058-main
COMPOSE_PROJECT_NAME=oreflow58 bash scripts/oreflow-start.sh
python3 tools/verify-oreflow.py
```

The new launcher avoids the unresolvable optional upstream Extended API Git commit and starts all five Ditto microservices before running initialization. This launcher is **not yet validated on a real Docker host for this release**, despite the offline simulation/API tests passing. If there is insufficient memory, check `docker stats`, `docker logs` and the status of the Ditto gateway before restarting anything. On a machine with ~3.7 GiB available RAM the five JVMs plus MongoDB can be constrained.

## What changed

- **24 hours by default** (selectable 4, 12, 24 or 48 hours); playback up to 360x. This is a precomputed simulation replay, not real-time fleet telemetry.
- **Estimated fuel** by truck class, fuel levels, modeled loaded/empty and idle rates, fuel queues, two assumed refueling stations (at L1 and L4), two pumps each at 45 L/min.
- **Planned maintenance and shift relief** at next service boundaries; values are clearly modeled assumptions.
- **Configurable What-If:** specific road (including reverse-direction roads), shovel, truck, fuel station, dump site, time/duration, truck counts per source fleet class, road degradation, fuel price and random seed.
- **Dispatch optimization objective:** more simulated tonnes, less total modeled diesel, or a balance. Total fuel and litres per tonne are *not the same objective*.
- **Three comparisons:** chosen vs nearest policy under the same disruption; normal vs changed with same policy; fuel and cost metrics.
- **Twin readback UI:** operator-friendly values with optional raw Ditto JSON. New fuel properties are sent to Ditto via the existing MQTT channel.
- **Grafana:** added two modeled fuel charts. Existing original dashboard provisioning remains intact.

## To validate the new run

Use a normal 24-hour run (seed 42): all 71 trucks should appear, fuel counters should rise as playback advances, fuel stations should be visited, and the completed-run metrics should show positive refueling events. Run What-If with **Road L3 → D5 at 08:00 for two hours**, **Shovel 3-1 at 08:00**, or **Fuel Station L4 at 10:50 for five hours**. For each, compare to normal under the same seed and policy. Click Digital Twins → Read T001; the response must come from the running Ditto, not from hardcoded text. Run `verify-oreflow.py` for true live interoperability evidence, including historical InfluxDB data.

## Known limits

There is **no real GPS/fuel/cost/ore-grade telemetry**. The manufacturer examples only inform reference-class tank sizes; truck type identities are not confirmed. The road grade proxies, engine fuel burn, fuel stations, maintenance windows and downtime are documented scenario assumptions. Truck breakdowns are applied at the next safe event boundary, not mid-road. A road closure prevents *new* entries; trucks already en route finish. Historical fuel events are generated by this simulation, not field logs. The simulator is still an independent OpenMines-derived engine, not the original OpenMines runtime. The extended-api (optional) is not automatically built.
