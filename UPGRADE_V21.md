# OreFlow KZ 2.1 — Upgrade instructions

**This is a complete Team 058 project, not a standalone frontend.** It is based on OreFlow KZ 2.0 and retains the OpenEgiz deployment, Eclipse Ditto, MQTT, Grafana, and original OpenMines configuration.

## Upgrade the existing `oreflow58` Docker stack on Windows + Ubuntu WSL

1. Download `OreFlow_KZ_Team058_V21_Operations_Intelligence.zip` into Windows `Downloads`.
2. In Ubuntu WSL:

```bash
mkdir -p ~/OreFlow_Team058_V21
unzip -o /mnt/c/Users/dzzen/Downloads/OreFlow_KZ_Team058_V21_Operations_Intelligence.zip -d ~/OreFlow_Team058_V21
cp ~/OreFlow_Team058_V2/team-058-main/deploy/compose/.env ~/OreFlow_Team058_V21/team-058-main/deploy/compose/.env
cd ~/OreFlow_Team058_V21/team-058-main
COMPOSE_PROJECT_NAME=oreflow58 bash scripts/oreflow-upgrade-running.sh
python3 tools/verify-oreflow.py
```

Then open `http://localhost:8099`. The existing Docker **volumes and platform services are preserved**. Keep your V2 folder until V2.1 passes verification on your host.

The upgrade script rebuilds only the OreFlow application image and recreates the OreFlow and Grafana presentation containers; it does **not** delete MongoDB, InfluxDB, Grafana, or MQTT volumes. If Docker was just restarted, run `COMPOSE_PROJECT_NAME=oreflow58 bash scripts/oreflow-start.sh` instead to bootstrap the whole cluster.

## New UI

- **Live Mine:** simulated equipment map, 71 clickable trucks, playback in 30/90/180 real seconds per complete run, hourly production and current truck states.
- **Dispatch Lab:** nearest vs selected dispatch policy comparisons, production curves, fuel intensity, queue times, genuine decision audit, 11-seed experiment.
- **What-If Studio:** simple disruption cards, existing routes/actual source equipment, time-of-day and duration selectors; technical settings are tucked under Advanced; 3 comparison types including actual scenario curves.
- **Digital Twins:** searchable truck list, real Ditto readback, current-run match, technical JSON only on demand.
- **Evidence & Data:** 24-hour production aggregates, summed truck-activity time, loading sites and truck-class fuel.
- **Operations Report:** six KPIs, hourly production and fuel, 20 shovel records, class summaries, CSV export and browser Print → Save PDF.

## Important evidence rules

The platform does **not** have physical truck GPS, payload, fuel or maintenance telemetry. Mine configuration is derived from an anonymized OpenMines example; runtime operations and fuel consumption are generated by OreFlow's simulator using explicitly assumed engineering rates. No real mine gains are claimed. The printed report is generated from the same run events as the simulator; no UI metrics are hardcoded. All shovel fuel metrics remain **unmodeled** (not zero).

## Local tests (without Docker)

```bash
cd team/oreflow
python3 -m unittest discover -s tests -v
cd ../..
python3 tools/test-v2-api.py
python3 tools/test_oreflow_http.py
```

Docker/real MQTT/real Ditto/real InfluxDB readback must still be verified on **your PC** with `python3 tools/verify-oreflow.py`. The local tests cannot certify those external connections.

## Revert

Stop V2.1 OreFlow container (preserve volumes), then from your existing V2 project run its `scripts/oreflow-upgrade-running.sh` with `COMPOSE_PROJECT_NAME=oreflow58`. Do not run `docker compose down -v` and do not delete volumes.
